# 근로기준법 RAG 검색 + MCP 실습

근로기준법을 조·항 단위로 검색해 근거 조항과 출처를 돌려주는 검색 파이프라인을 직접 만들고, Kotlin으로 만든 MCP 서버로 Claude 데스크톱 앱에 연결해 근거 조항을 바탕으로 답하게 한 실습입니다. 검색 방식(BM25, kNN, 하이브리드)과 도구 설명에 따라 결과가 어떻게 달라지는지 비교했습니다.

## 한눈에 보기

- **검색:** 근로기준법을 청크 205개로 나눠 Elasticsearch에 색인하고, 질문 20개(유형 5가지)와 검증용 질문 8개로 BM25·kNN·하이브리드를 비교했습니다. 정답 조문이 상위 5개 안에 든 질문 수(recall@5)는 kNN 18/20, 하이브리드 18/20, BM25 15/20이었고, 정답 순위(MRR)는 kNN이 가장 높았습니다.
- **검색 실험:** 청크 앞 상위 제목을 빼 보는 실험으로 그 효과를 확인했고(BM25 recall 15/20 → 10/20), 하이브리드(RRF) 설정을 조정한 뒤 튜닝에 쓰지 않은 질문으로 다시 확인해 검증된 개선만 반영했습니다.
- **MCP:** 검색 API를 호출하는 `search_labor_law` 도구를 Kotlin MCP 서버로 만들어 Claude 데스크톱 앱에 연결했습니다.
- **도구 설명 실험:** 코드는 그대로 두고 도구 설명만 바꿨는데, Claude의 도구 호출 시점, 검색어 구성, 출처 표시가 달라졌습니다. 검색어 하나에 주제 4개를 넣어 6위로 밀렸던 정답 조항이, 주제별로 나눠 검색하게 하자 1위로 올라왔습니다.
- **도구 실패 실험:** 검색 API를 끈 채로 질문해 보고 에러 문구를 다시 설계했습니다. 원인과 재시도 여부를 담자 헛된 재시도가 사라지고, 실패 안내가 답변 끝에서 첫 줄로 옮겨졌습니다.
- **확인한 것:** 검색이 정답을 놓쳐도 LLM이 학습한 지식과 웹 검색으로 빈자리를 채우면 최종 답변은 맞아 보입니다. 답변 품질과 별개로 검색 단계를 따로 평가해야 합니다.

## 구조

```
Claude 데스크톱 앱 (도구 선택, 답변 생성)
   │  stdio · JSON-RPC (tools/list, tools/call)
   ▼
Kotlin MCP 서버 ── search_labor_law 도구
   │  HTTP GET /search
   ▼
검색 API (Python, FastAPI) ── 질문 임베딩 (bge-m3)
   │
   ▼
Elasticsearch 9.3.8 ── nori 형태소 분석(BM25) + dense_vector(kNN)
```

질문 하나가 처리되는 순서입니다.

1. Claude가 도구 설명을 보고 `search_labor_law`를 고른 뒤, 검색어를 만들어 `tools/call`을 보냅니다. (예: "해고 예고")
2. MCP 서버가 검색 API에 `GET /search?q=해고 예고&k=5`를 보냅니다.
3. 검색 API가 검색어를 bge-m3로 임베딩하고, Elasticsearch에서 가장 가까운 청크 5개를 찾습니다.
4. MCP 서버가 결과를 조문 원문과 출처가 담긴 텍스트로 바꿔 돌려주고, Claude가 이를 근거로 답합니다.

## 1. 데이터 준비와 청킹

국가법령정보센터에서 받은 파일은 확장자가 .hwp지만 내용은 XML(HWPML)이라, 문단 텍스트를 직접 뽑았습니다. 머리말과 부칙을 빼고 제1장부터 마지막 조문까지 남겼습니다.

**청킹 규칙**

- 기본 단위는 조입니다. 조 하나가 주제 하나를 다뤄 의미가 잘 끊기지 않습니다.
- 500자를 넘는 조는 항 단위로 나눴습니다. 제60조(연차 유급휴가)를 통째로 넣으면, 연차 일수를 물었는데 다른 항까지 딸려 옵니다.
- 모든 청크 앞에 `근로기준법 > 제4장 근로시간과 휴식 > 제60조(연차 유급휴가)` 같은 상위 제목을 붙였습니다. 항만 떼어내면 "사용자는 … 주어야 한다"만 남아 무슨 내용인지 알 수 없기 때문입니다.
- 호(1. 2. …)는 직전 항에 붙였습니다. 호만 떼면 무엇에 대한 목록인지 알 수 없습니다.
- 삭제된 조·항과 `[본조신설 …]` 같은 개정 메모는 뺐습니다.
- 청크마다 검색·임베딩용 `content`(상위 제목 + 원문)와 근거 표시용 `text`(원문만)를 따로 두었습니다.

**출처 메타데이터:** 청크마다 법 이름, 시행 버전(시행 2026. 10. 8., 법률 제21533호), 장, 조, 항을 저장했습니다. 법이 바뀌어도 어느 버전을 근거로 답했는지 알 수 있게 하려는 것입니다.

**결과:** 조 131개 → 청크 205개 (항 단위로 나뉜 조 21개)

| 기준 길이 | 청크 수 | 항 단위로 나뉜 조 | 중간 길이 | 최대 길이 |
|---|---|---|---|---|
| 500자 (채택) | 205 | 21 | 154 | 685 |
| 300자 | 232 | 35 | 142 | 685 |

최대 길이가 같은 이유는 가장 긴 청크(제2조① 정의 조항)가 항 하나에 호 9개가 붙은 형태라, 항 단위로는 더 나눌 수 없기 때문입니다.

**발견한 버그:** 제116조 끝의 `[시행일: 2027. 1. 1.] 제116조제1항제2호`는 대괄호 뒤에 글자가 더 있어 개정 메모로 걸러지지 않았고, 삭제된 항에 붙어 의미 없는 청크가 생겼습니다. 메모를 판단하는 규칙을 "대괄호로 끝나는 줄"에서 "대괄호로 시작하는 줄"로 바꿔 해결했습니다(청크 206개 → 205개). 결과 파일을 직접 열어 확인하다가 찾았습니다.

## 2. 색인

| 필드 | 타입 | 용도 |
|---|---|---|
| `id`, `article`, `paragraph` 등 | keyword | 분석하지 않고 값 그대로 저장. 특정 조만 거를 때 사용 |
| `content`, `title` | text + nori | 형태소 단위로 색인. BM25 키워드 검색 대상 |
| `text` | text (`index: false`) | 색인하지 않고 저장만 함. 답변에 원문을 보여줄 때 사용 |
| `embedding` | dense_vector (1024차원, 코사인, HNSW) | kNN 검색 대상 |

- nori는 "연차휴가를 사용했다"를 연차 / 휴가 / 사용으로 나눕니다. 형태소 분석 없이 색인하면 "연차"로 검색해도 "연차휴가를"이 걸리지 않습니다.
- dense_vector는 기본적으로 벡터를 압축(양자화)해 저장하지만, 데이터가 205개로 작아 압축 없는 HNSW로 정확도를 우선했습니다.
- 문서 id를 청크 id(예: `제60조①`)로 써서, 다시 실행해도 중복 없이 덮어씁니다.
- M1 GPU(MPS)에서 205개를 임베딩하는 데 약 14초 걸렸습니다.

## 3. 검색 비교

- **BM25:** `content` 필드에 대한 match 쿼리
- **kNN:** 질문을 색인 때와 같은 모델·정규화로 임베딩해 코사인 유사도 상위 k개를 찾음 (num_candidates 100)
- **하이브리드:** 두 검색 결과를 RRF(순위 r마다 가중치 / (60 + r)을 더함)로 직접 합칩니다. 각 검색에서 10개씩 가져오고 BM25 쪽 가중치는 0.5입니다(아래 "하이브리드 조정과 검증" 참고).

### 평가 방법

- 질문 20개를 유형 5가지로 나눠 만들었습니다: 조 번호·제목 4, 법률 용어 4, 항 단위 4, 일상 표현 6, 주제 섞임 2. 주제 섞임에는 MCP 실험에서 Claude가 실제로 보낸 검색어를 넣었습니다.
- 정답이 "제60조"처럼 조 번호면 그 조의 어느 청크든 찾으면 맞힌 것으로, "제60조②"처럼 항까지 있으면 그 항 청크를 찾아야 맞힌 것으로 채점합니다.
- **recall@5:** 정답이 상위 5개 안에 든 질문 수입니다. 상위 5개만 LLM에 넘기므로 가장 먼저 보는 지표입니다.
- **MRR:** 정답 순위의 역수 평균입니다(1위 1점, 2위 0.5점, 못 찾으면 0점). 정답을 얼마나 위에 올렸는지 봅니다.
- 하이브리드 설정을 고르는 데 쓰지 않은 검증용 질문 8개를 따로 두었습니다.

### 결과 (질문 20개)

| 유형 | BM25 | kNN | 하이브리드 기존 설정 | 하이브리드 조정 후 |
|---|---|---|---|---|
| 조 번호·제목 (4) | 4/4 | 4/4 | 4/4 | 4/4 |
| 법률 용어 (4) | 4/4 | 4/4 | 4/4 | 4/4 |
| 항 단위 (4) | 4/4 | 4/4 | 4/4 | 4/4 |
| 일상 표현 (6) | 1/6 | 5/6 | 4/6 | 6/6 |
| 주제 섞임 (2) | 2/2 | 1/2 | 2/2 | 2/2 |
| **recall@5** | 15/20 | 18/20 | 18/20 | **20/20** |
| **MRR** | 0.589 | **0.838** | 0.664 | 0.823 |

하이브리드 기존 설정은 후보 20개, BM25 가중치 1.0이고, 조정 후는 후보 10개, BM25 가중치 0.5입니다. 조정 후 설정은 이 20개 질문으로 골랐기 때문에 검증용 질문으로 따로 확인했습니다.

- 조 번호·제목, 법률 용어, 항 단위 질문은 모든 방식이 찾았고, 차이는 일상 표현과 주제 섞인 질문에서 났습니다.
  - 일상 표현에서는 "따돌리면" ↔ "괴롭힘", "나오지 말라고" ↔ "해고"처럼 겹치는 단어가 없어 BM25가 약했습니다.
  - 주제 섞인 질문에서는 kNN이 검색어 전체를 벡터 하나로 만들어, "해고의 예고 서면통지 부당해고 구제신청"의 정답(제26조)을 놓쳤습니다. BM25는 "해고의 예고"라는 문구가 그대로 겹쳐서 찾았습니다.
- 항 단위 질문 4개는 kNN이 모두 1위로 찾았습니다. 긴 조를 항 단위로 나눈 청킹이 제 역할을 합니다.
- "점심시간은 법으로 얼마나 보장돼?"(정답 제54조 휴게)는 기존 세 방식 모두 못 찾았습니다. 조문은 "휴게시간"이라고 씁니다.
- 처음 질문 8개로 비교했을 때는 하이브리드(7/8)가 kNN(8/8)보다 낮았지만, 20개에서는 같아졌습니다. 두 검색이 강한 질문이 다르다는 하이브리드의 근거가 20개에서야 보였습니다. 평가 질문의 수와 구성에 따라 결론이 달라질 수 있습니다.

### 상위 제목을 빼면

청크 앞에 붙인 상위 제목(`근로기준법 > 제4장 근로시간과 휴식 > 제60조(연차 유급휴가)`)이 실제로 도움이 되는지 보려고, 이 줄만 빼고 원문만으로 색인한 비교용 인덱스를 따로 만들어 같은 질문으로 비교했습니다(`index.py --no-header`). 청크, 임베딩 모델, 검색 코드는 같습니다.

| 질문 20개 | BM25 | kNN | 하이브리드 기존 설정 |
|---|---|---|---|
| recall@5 (상위 제목 있음 → 없음) | 15 → **10** | 18 → 18 | 18 → 18 |
| MRR | 0.589 → 0.306 | 0.838 → 0.739 | 0.664 → 0.508 |
| 조 번호·제목 질문 4개의 MRR | 0.875 → **0.133** | 1.000 → **0.521** | 0.875 → 0.396 |

- 조 번호와 조 제목의 단어는 상위 제목에만 있어서, 빼면 BM25가 크게 떨어졌습니다. 예를 들어 항 단위로 나뉜 제60조②의 원문에는 "연차"와 "제60조"가 없습니다.
- kNN은 본문만으로도 뜻을 잡아 recall을 유지했지만, 조 번호·제목으로 찾는 질문에서 순위가 크게 떨어졌습니다.
- 사용자는 규정 번호나 제목으로 찾는 경우가 많아, 청크마다 상위 제목을 붙이는 설계가 실무에서 특히 중요합니다.

### 하이브리드 조정과 검증

- 기존 설정(후보 20개)에서는 한쪽 검색에서만 1위인 문서(1/61 ≈ 0.0164)보다 두 검색 후보에 모두 20위로 걸친 문서(1/80 + 1/80 = 0.025)가 항상 점수가 높아, BM25가 빗나간 질문에서 kNN이 찾은 정답이 밀려났습니다.
- RRF 상수(1·10·30·60), 후보 수(5·10·20·50), BM25 가중치(1.0·0.5·0.3)의 48개 조합을 비교했습니다(`search.py --sweep`). 후보를 10개로 줄이자 양쪽에 우연히 걸치는 엉뚱한 문서가 줄어 recall이 20/20이 됐고, BM25 가중치를 0.5로 낮추자 MRR이 0.823으로 올랐습니다.
- 같은 질문으로 설정을 고르고 평가하면 그 질문들에만 맞는 설정을 고를 위험(과적합)이 있어, 튜닝에 쓰지 않은 질문 8개로 다시 확인했습니다(`search.py --holdout`).

| 검증용 질문 8개 | BM25 | kNN | 하이브리드 기존 설정 | 하이브리드 조정 후 |
|---|---|---|---|---|
| recall@5 | 4/8 | 8/8 | 8/8 | 8/8 |
| MRR | 0.333 | **0.938** | 0.577 | 0.692 |

- 조정한 설정은 두 질문 묶음 모두에서 기존 하이브리드보다 나아서, 하이브리드 설정을 바꿨습니다.
- kNN보다 recall이 높았던 것은 검증용 질문에서 재현되지 않았고, 순위는 두 묶음 모두 kNN이 높았습니다. 그래서 검색 API의 기본 방식은 kNN으로 유지했습니다.

## 4. 검색 API

- `GET /search?q=…&mode=knn|bm25|hybrid&k=5`, `GET /health`
- 응답에 조문 원문(`text`)과 출처 문구(`source`, 예: `근로기준법 제26조 (시행 2026. 10. 8., 법률 제21533호)`)를 함께 담았습니다.
- 기본 검색 방식은 kNN입니다. 평가에서 정답 순위(MRR)가 가장 좋았습니다(3장).
- 서버를 시작할 때 임베딩 모델을 미리 불러와, 첫 요청이 느려지지 않게 했습니다.
- 검색과 답변 생성을 분리해 두어, MCP 서버든 나중에 붙일 다른 클라이언트든 같은 API를 쓰면 됩니다.

## 5. MCP 서버 (Kotlin)

- MCP Kotlin SDK의 stdio 방식으로 만들었습니다. Claude 앱이 서버 프로그램을 직접 실행하고, 표준 입출력으로 JSON-RPC 메시지를 주고받습니다.
- 검색 로직은 Python 쪽에만 두고, MCP 서버는 Claude 앱과 검색 API를 잇는 어댑터 역할만 합니다.
- **도구 정의:** Claude가 `tools/list`로 받아 가는 정보는 이름, 설명, 입력 스키마입니다. Claude는 이 정보만 보고 언제 도구를 쓸지, 무엇을 넣을지 정합니다.
  - 이름: `search_labor_law`
  - 입력: `query`(필수, 문자열), `k`(1~10, 기본 5)
  - annotations: `readOnlyHint: true` (데이터를 바꾸지 않는 도구)
- **결과 형식:** 검색 API의 JSON을 Claude가 바로 근거로 쓸 수 있게, 조항·출처·원문 순서의 텍스트로 바꿨습니다.

  ```
  검색어: 해고 예고
  근로기준법 검색 결과 5건

  [1] 근로기준법 제26조 (해고의 예고)
  출처: 근로기준법 제26조 (시행 2026. 10. 8., 법률 제21533호)
  원문:
  사용자는 근로자를 해고(경영상 이유에 의한 해고를 포함한다)하려면 적어도 30일 전에 예고를 하여야 하고, ...
  ```

- **에러 처리:** 실패하면 `isError: true`와 함께, 예외 종류별로 원인·재시도할 만한지·실패했을 때 할 일을 담은 문구를 돌려줍니다. 연결 실패와 5xx는 "재시도하지 마세요", 시간 초과와 4xx는 "한 번만 다시 시도하세요"이고, 끝에 "다른 출처로 추측하지 말고 확인할 수 없다는 사실을 먼저 알리세요"를 붙입니다. 예외 이름이나 서버 이름 같은 운영자용 정보는 stderr 로그로만 남깁니다.
- **stdout 주의:** stdout은 JSON-RPC 메시지 전용이라 `println`을 쓰면 통신이 깨집니다. 로그는 stderr로 보냈습니다.
- Claude 앱에 연결하기 전에 JSON-RPC 메시지(initialize → notifications/initialized → tools/list → tools/call)를 직접 보내 응답을 확인했습니다.

## 6. 도구 설명에 따른 Claude 행동 비교

LLM은 도구의 이름과 설명을 보고 언제 도구를 쓸지, 검색어를 어떻게 만들지 정합니다. 코드는 그대로 두고 도구 설명만 두 가지로 바꿔, Claude 데스크톱 앱에서 같은 질문 3개를 새 채팅마다 물어봤습니다. 연결한 도구는 labor-law 하나이고, 웹 검색과 메모리는 채팅마다 끌 수 없어 켜진 채로 두 버전을 같은 조건에서 비교했습니다.

- **V1:** "근로기준법 조항을 검색합니다." (검색어 설명: "검색어")
- **V2:** 근로기준법 관련 질문에는 기억 대신 이 도구로 근거를 찾을 것, 일상 표현은 법률 용어로 바꿔 검색할 것, 주제가 여러 개면 나눠서 검색할 것, 답변에 조·항 출처를 표시할 것 ([`Main.kt`](mcp-server/src/main/kotlin/Main.kt))

| 질문 | V1 | V2 |
|---|---|---|
| 근로기준법상 연차 유급휴가는 며칠이야? | 도구 1회 + 웹 검색. "상시 5명 이상 사업장 적용"은 웹에서 가져옴 | 도구 2회(연차 일수 / 5명 미만 적용 범위), 웹 검색 없음. 문장마다 조·항 출처 표시 |
| 회사가 갑자기 내일부터 나오지 말래. 원래 미리 알려줘야 하는 거 아니야? | 웹 검색 후 도구 1회. 검색어 하나에 주제 4개를 넣어 정답(제26조)이 6위로 빠짐. 핵심 내용은 웹으로 채움 | 주제별로 도구 4회, 네 번 모두 정답 조항 1위. 제26조 단서의 예외 3가지를 원문대로 인용 |
| 오늘 저녁 메뉴 추천해줘 | 도구 호출 없음 | 도구 호출 없음 |

V1에서 Claude가 보낸 검색어 "해고의 예고 서면통지 부당해고 구제신청"을 검색 방식별로 다시 돌려, 제26조의 순위를 비교했습니다.

| kNN | BM25 | 하이브리드 | "해고의 예고"만 넣었을 때 (kNN) |
|---|---|---|---|
| 6위 | 5위 | 5위 | 1위 |

- 도구 설명만 바꿔도 도구 호출 시점, 검색어 구성, 출처 표시가 달라졌습니다.
- 주제가 섞인 검색어에서는 세 방식 모두 제26조를 5~6위에 두었습니다. kNN은 검색어 전체를 벡터 하나로 만들기 때문에, 주제 4개 중 3개(서면통지, 부당해고, 구제신청)가 가리키는 구제 절차 쪽으로 벡터가 쏠렸습니다. 검색 방식을 바꾸는 것보다 검색어를 주제별로 나누는 효과가 커서, 이 결과를 V2 설명에 반영했습니다.
- V1의 해고 질문은 검색이 정답을 놓쳤는데도 최종 답변은 맞았습니다. Claude가 학습한 지식과 웹 검색으로 빈자리를 채웠기 때문입니다. 답변만 봐서는 검색 실패를 알 수 없어, 검색 단계를 따로 평가해야 합니다. 사내 데이터처럼 LLM이 모르는 내용이라면 이런 실패가 그대로 틀린 답으로 이어집니다.
- V2 설명의 "반드시 이 도구로"는 "근로기준법과 관련된 질문에는"으로 범위를 정해 두어, 상관없는 질문에는 도구를 부르지 않았습니다.

## 7. 도구가 실패할 때

검색 API(uvicorn)를 끈 채로 Claude 앱에서 "근로기준법상 연차 유급휴가는 며칠이야?"를 물었습니다. 처음에는 도구가 `근로기준법 검색 API 호출에 실패했습니다: null. 검색 API(uvicorn)가 실행 중인지 확인하세요.`를 돌려줬습니다. JDK HttpClient의 연결 실패 예외는 메시지가 비어 있는 경우가 있어 "null"이 찍혔습니다.

에러 문구도 Claude가 읽고 다음 행동을 정하는 입력이라고 보고, 도구 설명은 그대로 둔 채 에러 처리만 바꿨습니다.

- 예외 종류별로 원인, 다시 시도할 만한지, 실패했을 때 할 일을 담았습니다. 연결 실패와 5xx는 "재시도하지 마세요", 시간 초과는 "한 번만 다시 시도하세요"이고, 끝에 "다른 출처로 추측하지 말고 확인할 수 없다는 사실을 먼저 알리세요"를 붙였습니다.
- 예외 이름, 서버 이름 같은 운영자용 정보는 사용자에게 전달될 수 있는 문구에서 빼고 stderr 로그로만 남겼습니다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 재시도 | 검색어를 바꿔 1번 | 없음 |
| 실패 안내 위치 | 답변 맨 끝 | 답변 첫 줄 |
| 개발자용 정보 노출 | "uvicorn이 꺼져 있는 것 같아요" | 없음 |
| 웹으로 대신 답하기 | 함 | 여전히 함 (웹 자료라고 먼저 밝힘) |

- "재시도하지 마세요"는 따랐지만 "웹으로 대신 찾지 마세요"는 따르지 않았습니다. 도구 결과는 외부 데이터라, 그 안의 지시를 LLM이 무조건 따르면 프롬프트 인젝션에 취약해집니다. "웹 금지" 같은 정책은 도구 결과가 아니라 시스템 프롬프트나 도구 구성으로 정해야 합니다.
- 같은 질문, 같은 조건에서도 실행할 때마다 행동 순서가 달랐습니다(한 번은 도구 먼저, 한 번은 웹 검색 먼저). 한 번 실행한 결과로 단정하면 안 됩니다.
- 입력 스키마에 k의 최대값을 10으로 적었지만 25가 그대로 검색 API까지 갔습니다. 입력 스키마는 LLM에게 주는 안내일 뿐 검증 장치가 아니라서, 서버에서 직접 검증해야 합니다.

## 한계와 개선 아이디어

- **평가 규모:** 평가 질문이 튜닝용 20개, 검증용 8개라 숫자를 일반화하기에는 여전히 적습니다. Claude 앱 실험은 질문마다 한두 번씩만 돌렸습니다.
- **용어 차이:** 사용자는 "점심시간"이라고 묻는데 조문은 "휴게시간"이라고 써서 어떤 방식으로도 찾지 못했습니다. 동의어 사전(Elasticsearch synonym 필터)이나 LLM의 검색어 재작성이 필요하고, 사내 시스템이라면 사내 용어 사전이 필요한 지점입니다.
- **데이터 범위:** 법률만 색인해서, 시행령에 있는 내용(5명 미만 사업장에 적용되는 조항 목록)은 도구로 답하지 못했습니다. 답변 범위는 색인한 데이터 범위를 넘지 못합니다.
- **조 간 참조:** 벌칙 조문(제110조)은 "제26조 … 를 위반한 자"처럼 조 번호를 늘어놓은 형태라, 의미 검색으로 잘 잡히지 않습니다("해고 예고 위반 벌칙"으로 검색하면 4위). 청킹할 때 조 간 참조 관계를 메타데이터로 뽑아 두면, 제26조를 찾을 때 관련 벌칙도 함께 돌려줄 수 있습니다.
- **웹 검색 혼입:** Claude 앱에서는 웹 검색을 끌 수 없어 답변에 웹 내용이 섞였습니다. 직접 만드는 에이전트(Claude API 등)에서는 도구 목록을 정할 수 있어, 사내 데이터 도구만 쓰게 할 수 있습니다.
- **검색 개선 후보:** 재정렬(reranking) 모델, 서버에서 검색어를 주제별로 나눠 검색(multi-query), 동의어 사전

## 실행 방법

```bash
# 1. Elasticsearch + nori
docker build -t es-nori:9.3.8 es/
docker run -d --name es-rag -p 9200:9200 \
  -e "discovery.type=single-node" -e "xpack.security.enabled=false" \
  -e "ES_JAVA_OPTS=-Xms1g -Xmx1g" es-nori:9.3.8

# 2. Python 환경
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 3. 데이터 준비와 색인 (data/labor_law.txt가 저장소에 포함되어 있어 chunk.py부터 실행해도 됩니다)
python chunk.py data/labor_law.txt data/chunks.jsonl
python index.py data/chunks.jsonl

# 4. 검색 비교
python search.py --eval                                        # 질문 20개, recall@5와 MRR
python search.py --holdout                                     # 검증용 질문 8개
python search.py --sweep                                       # 하이브리드(RRF) 설정 48개 조합 비교
python index.py data/chunks.jsonl --index labor_law_noheader --no-header   # 상위 제목 없는 비교용 인덱스
python search.py --eval --index labor_law_noheader

# 5. 검색 API
uvicorn api:app --port 8000
# http://localhost:8000/docs

# 6. MCP 서버 빌드
cd mcp-server && ./gradlew installDist
# → build/install/labor-law-mcp/bin/labor-law-mcp 를 Claude 데스크톱 앱 설정(mcpServers)에 등록
```

## Claude 데스크톱 앱 연결

`claude_desktop_config.json`의 `mcpServers`에 등록합니다. 앱이 MCP 서버를 직접 실행하고 stdio로 JSON-RPC 메시지를 주고받습니다. Claude 앱은 터미널 설정(.zshrc)을 읽지 않아서, JDK 경로를 `env`로 지정합니다.

```json
{
  "mcpServers": {
    "labor-law": {
      "command": "/절대경로/rag-practice/mcp-server/build/install/labor-law-mcp/bin/labor-law-mcp",
      "env": { "JAVA_HOME": "/JDK17 경로/Contents/Home" }
    }
  }
}
```

검색 API(`uvicorn api:app --port 8000`)가 실행 중이어야 도구가 결과를 돌려줍니다.
